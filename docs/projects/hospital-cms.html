CASE-02보안 사례2023.04–2025.03

대형병원 키오스크 CMS의 권한 결함 수정과 보안점검 대응

대형병원 키오스크를 원격으로 관리하는 CMS를 혼자 만들어 운영했고, 세션 검증보다 권한 부여가 먼저 일어나던 결함을 고쳐 병원 보안점검을 통과했습니다.

역할
CMS 단독 설계, 개발, 운영과 보안점검 대응
직무
보안, 개발

대응 흐름

  1. 01요청관리자나 운영자가 CMS에 로그인해 요청을 보냅니다
  2. 02세션 검증Redis에서 세션을 먼저 확인합니다
  3. 03권한 부여검증이 끝난 세션에만 역할 권한을 붙입니다
  4. 04원격 제어WebSocket으로 키오스크 화면을 보고 명령을 보냅니다
  5. 05배포예약과 그룹 단위로 배포하고 문제가 생기면 롤백합니다

해결한 문제

  1. 문제

    세션 검증 전에 임시 권한이 붙는 구간

    쓴 것

    권한 부여를 세션 검증 뒤로 옮김

    효과

    검증되지 않은 세션이 권한을 쥐는 구간을 없앰

  2. 문제

    병원의 계정 정책 요구

    쓴 것

    정기 변경, 실패 횟수 제한, 재사용 금지, 계정 잠금

    효과

    납품한 CMS 전체가 병원 보안점검 통과

  3. 문제

    장애마다 현장으로 가야 하는 운영

    쓴 것

    WebSocket 화면 미러링과 원격 명령

    효과

    원격으로 풀 수 있는 장애는 CMS에서 처리

  4. 문제

    외부 인증기관 접속이 막힌 망분리 환경

    쓴 것

    NICE CPClient, Electron 앱, IIS와 .NET 로컬 인증 서버를 콜백으로 연결

    효과

    망분리 안에서 본인인증 흐름 배포

전과 후

권한 부여 순서

−전요청, 임시 권한 부여, 세션 검증

+후요청, 세션 검증, 권한 부여

계정 정책

+결과정기 변경, 실패 횟수 제한, 재사용 금지, 계정 잠금

키오스크 장애 처리

−전담당자가 현장으로 이동

+후원격으로 풀 수 있는 장애는 CMS로 처리

배경

상황

고객은 4만 평 규모의 대형병원이었습니다. 병원 내부망의 키오스크 약 200대는 장애가 날 때마다 담당자가 현장으로 가야 했습니다. 이 부담을 줄이려고 원격 관리 CMS를 혼자 만들어 운영했습니다. CMS에는 화면 미러링과 원격 명령, 예약 배포를 넣었습니다.

납품하는 CMS는 병원 보안점검을 통과해야 했고, 권한 분리와 계정 정책을 병원 기준에 맞춰야 했습니다.

어떻게 알았나

병원 보안 요구에 맞춰 인증과 권한 구조를 고치던 중에, Redis에서 세션 검증이 끝나기 전에 임시 권한이 먼저 붙는 구간을 찾았습니다. 요청 타이밍에 따라 검증되지 않은 세션이 권한을 쥘 수 있는 구조였습니다.

내가 한 것

  • 권한 부여를 세션 검증 뒤로 옮겨 처리 순서를 바로잡았습니다.
  • 서버 개인키로 서명하는 JWT 인증과 bcrypt 비밀번호 해시, 관리자와 운영자 역할을 나눈 RBAC를 구현했습니다.
  • 90일마다 비밀번호를 바꾸게 하고, 로그인 실패 횟수 제한과 재사용 금지, 계정 잠금 정책을 적용했습니다.
  • ORM으로 쿼리를 만들어 SQL을 직접 조립하는 곳을 줄였습니다.
  • 연동 문제는 브라우저 개발자 도구의 Network 탭에서 엔드포인트와 요청 내용, Authorization 헤더의 JWT를 확인하며 분석했습니다.

갖춘 것

  • 화면 미러링

    키오스크 화면을 CMS에서 그대로 봅니다

  • 원격 명령

    재시작 같은 명령을 현장에 가지 않고 보냅니다

  • 예약 배포와 롤백

    그룹 단위로 예약 배포하고 중단점으로 되돌립니다

  • 역할 권한

    관리자와 운영자의 권한을 나눕니다
