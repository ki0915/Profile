서버 7대 통합과 백업 재설계 (BCP/DR)

노후 서버 7대를 Windows Server 2022와 Hyper-V로 합치고, 스냅샷 하나에 기대던 복구를 여러 겹으로 바꿨습니다. 퇴사 직후 랜섬웨어 사고에서 회사는 이 백업으로 데이터 손실 없이 하루 만에 복구했습니다.

사내 인프라 작업이라 공개 저장소가 없습니다.

요약

노후 서버 7대를 Windows Server 2022와 Hyper-V로 합치면서 인바운드를 기본 차단하고, 웹 서버와 DB에 외부에서 바로 붙던 원격 접속을 없앴습니다. Hyper-V 스냅샷 하나뿐이던 복구 수단은 변경 제한 백업, AWS 서버 이미지, MSSQL 복제, API 이중화로 나눴습니다. 퇴사 직후인 2025년 4월 랜섬웨어 사고에서 회사는 이 체계로 데이터 손실 없이 하루 만에 복구했습니다.

명세

기간2023.04 – 2025.03
역할서버 점검, 가상화 재설계와 이관, 백업과 이중화 설계, 절차 문서화
환경사내 온프레미스 서버 7대
기술Windows Server 2022, Hyper-V, IIS, MSSQL 복제, AWS 서버 이미지, 방화벽 정책
저장소해당 없음 (실무, 소스 비공개)

배경

사내 서버 7대는 오래된 장비였습니다. 웹 서버와 DB에는 외부에서 바로 원격 접속할 수 있었고, 출결 서버는 Windows XP 기반이었습니다.

장애가 나면 기댈 수 있는 것은 Hyper-V 스냅샷 하나였습니다. DB 사본이나 클라우드 사본은 없었습니다.

한 일

서버 통합과 접근 경로 정리

  • 서버 7대의 역할과 외부 노출 상태를 하나씩 점검한 뒤 Windows Server 2022와 Hyper-V 환경으로 통합하고 이관했습니다.
  • 방화벽 정책은 인바운드를 기본 차단하고, 아웃바운드는 필요한 것만 허용하는 기준으로 다시 짰습니다.
  • 웹 서버와 DB에 외부에서 바로 들어오던 원격 접속을 없애고, 내부망 경로로만 접근하게 했습니다.
  • Windows XP 기반 구형 출결 서버를 새로 개발해 IIS에 올리고 인트라넷 DB와 연동했습니다.

백업을 여러 겹으로

바꾸기 전바꾼 뒤
Hyper-V 스냅샷 하나별도 볼륨에 쓰기를 제한한 변경 제한 백업
클라우드 사본 없음AWS 서버 이미지
DB 사본 없음MSSQL 복제
API 이중화 없음API가 실패하면 이중화 서버로 전환
–복구 절차 문서, 백업 접근은 사내 게이트웨이 IP 중심으로 제한

팀원 설득

사내 PC 이미지를 주기적으로 백업 시스템에 올리는 일에는 번거롭다는 반발이 있었습니다. 백업이 왜 필요한지만 말하지 않고, 그 이미지로 테스트 서버를 바로 띄우면 테스트가 빨라진다는 점을 함께 보여 줬습니다. 절차가 불편하지 않도록 문서로 정리해 두었습니다.

결과

제가 퇴사한 직후인 2025년 4월, 회사에 랜섬웨어 사고가 났습니다. 복구는 회사가 진행했고, 재직 중 설계한 백업 체계를 써서 데이터 손실 없이 하루 만에 복구를 마쳤습니다.

저는 백업 체계를 설계하고 구현했으며, 그 사고의 복구 작업을 직접 한 사람은 아닙니다. 수치는 사고 뒤 회사 기록에 근거합니다. 변경 제한 백업은 별도 볼륨에 쓰기를 제한한 구성이며, 인증된 WORM 스토리지는 아닙니다.
