CASE-01보안 사례2023.04–2025.03

고객사 웹 서버 침해사고 두 건 대응과 AWS 재구축

KISA 침해 통보와 서비스 중단 신고로 시작된 두 사고에 현장에서 대응하고, 무결성을 확인한 데이터만 AWS로 옮겨 서버를 다시 세웠습니다.

역할
현장 대응, 로그 분석, 복구와 AWS 재구축, 고객 보고
직무
보안, 인프라

대응 흐름

  1. 01통보와 신고1차는 KISA의 침해 통보, 2차는 서비스가 멈췄다는 고객 신고로 시작했습니다
  2. 02접근 되찾기시스템 접근과 관리자 계정을 되찾아 로그와 프로세스를 볼 수 있게 했습니다
  3. 03원인 추적IIS 로그를 따라가 응용프로그램 풀 안의 악성 실행을 찾았습니다
  4. 04데이터 분리MSSQL 데이터를 격리된 PC로 옮겨 무결성을 확인했습니다
  5. 05다시 세우기AWS EC2와 RDS에 새로 세우고 운영 IP만 열었습니다

해결한 문제

  1. 문제

    백업 복원이 중간에 멈춤

    쓴 것

    멈춘 지점을 따라가 업로드 파일을 점검

    효과

    검증 없이 저장된 과대 크기 악성 이미지를 분리하고 복원을 마침

  2. 문제

    보안 비용을 걱정하는 고객사

    쓴 것

    비용과 걸리는 시간을 그래프와 도형으로 정리

    효과

    클라우드 이관과 주기적인 서버 관리에 합의

  3. 문제

    VPN을 쓸 수 없는 구간

    쓴 것

    서비스 포트와 출발지 IP를 한정

    효과

    외부에 열린 범위를 줄임

전과 후

서버

−전고객사 Windows 서버와 오래된 ASP.NET

+후AWS EC2와 RDS로 재구축

관리 접근

+결과운영 IP 허용목록만 열고 RDP 차단

업로드 파일

−전검증 없이 저장

+후파일과 입력 무결성 검증 뒤 저장

복구

+결과사고 인지부터 복구까지 4일

같은 원인의 재발

+결과재직 중 확인되지 않음

배경

상황

미디어솔루션은 병원, 컨벤션센터, 호텔 같은 기업 고객의 키오스크 CMS와 운영 서버를 맡는 소기업이었습니다. 한 고객사의 웹 서버는 오래된 ASP.NET 위에서 돌고 있었고, 이 서버에서 침해사고가 두 번 일어났습니다. 두 사고 모두 제가 현장에 나가 대응했습니다.

어떻게 알았나

1차 사고는 KISA가 고객사 서버의 침해를 통보해 알게 됐습니다.

2차 사고는 서비스가 멈췄다는 고객 신고로 시작됐습니다. 서버의 CPU와 메모리가 비정상적으로 점유돼 있었고 공격자가 설치한 가상화 환경이 있어, 서버 자원을 몰래 쓰는 크립토마이닝을 의심했습니다.

무엇부터, 왜

무엇이 남아 있는지 보려면 시스템 접근과 관리자 계정부터 되찾아야 했습니다. 이 단계 없이는 로그도 프로세스도 확인할 수 없었기 때문입니다.

고객에게 조치가 필요한 이유를 설명할 때는 기존 .NET Framework 버전과 업데이트 버전의 공개 CVE 수, 사고 빈도를 근거로 삼았습니다. 이 자료로 AI를 활용해 위험 감소 추정치를 만들었고 출처를 함께 남겼습니다.

내가 한 것

  • 현장에서 시스템 접근과 관리자 계정을 되찾고, IIS 로그를 따라가 응용프로그램 풀 안의 악성 실행을 루트킷으로 판단했습니다.
  • 구형 미들웨어와 ASP.NET 관련 취약점을 점검하고 조치했습니다.
  • MSSQL 데이터는 내부망의 격리된 PC로 옮겨 무결성을 확인한 뒤 분리했습니다.
  • 2차 사고 복구 중 MSSQL 백업 복원이 멈춘 원인을 찾아, 업로드 검증 없이 저장된 과대 크기의 악성 이미지 파일을 분리하고 제거했습니다.
  • 웹 애플리케이션을 AWS EC2에 새로 세우고 DB를 RDS로 옮겼습니다. 보안그룹은 운영 IP 허용목록만 열고 RDP 접근을 막았습니다.

함께 고친 과정

기술 담당자에게는 취약한 구성과 코드 문제를, 경영진에게는 서비스 중단과 복구 비용 관점의 권고를 따로 설명했습니다.

파트너사 담당자는 보안 조치에 드는 비용과 재발을 걱정했고, 서비스 복구 말고는 관심이 크지 않았습니다. 그래서 비용과 걸리는 시간을 그래프와 도형으로 보여 줬습니다. 설명을 들은 고객은 클라우드 이관과 주기적인 서버 관리에 합의했습니다.

확인과 재발 방지

파일과 입력 무결성 검증을 강화한 서버를 다시 배포했습니다. VPN을 쓸 수 없는 구간은 서비스 포트와 출발지 IP를 한정했습니다. AWS로 옮긴 뒤 제가 재직하는 동안 같은 원인의 공격은 다시 확인되지 않았습니다.
