고객사 웹 서버 침해사고 2건 대응과 AWS 재구축

KISA 침해 통보와 서비스 중단 신고로 시작된 두 사고에 현장 대응했습니다. 두 번째 사고 뒤에는 서버를 새로 세우는 쪽으로 의사결정을 도왔고, 무결성을 확인한 데이터만 AWS EC2와 RDS로 옮겼습니다.

실무 프로젝트라 소스와 고객사 정보는 공개하지 않습니다.

요약

고객사 웹 서버가 두 번 침해됐고, KISA 통보와 서비스 중단 신고로 시작된 두 사고에 모두 현장 대응했습니다. IIS 로그로 루트킷 실행을 추적하고, CPU와 메모리 과점유에서 크립토마이닝 의심 징후를 확인했습니다. 재구축 의사결정을 도운 뒤 무결성을 확인한 MSSQL 데이터만 AWS EC2와 RDS로 옮겼고, 기록상 인지부터 복구까지 4일이 걸렸습니다.

배경

1차 사고: KISA 침해 통보

KISA에서 고객사 서버가 침해됐다는 통보를 받고 현장에 나갔습니다. 무엇이 남아 있는지 보려면 시스템 접근과 관리자 계정부터 되찾아야 했습니다.

2차 사고: 서비스 중단 신고

이번에는 서비스가 멈췄다는 고객 신고였습니다. 서버의 CPU와 메모리가 비정상적으로 점유돼 있었고, 공격자가 설치한 가상화 환경도 발견됐습니다. 서버 자원을 몰래 쓰는 크립토마이닝을 의심할 만한 징후였습니다. 웹 애플리케이션은 오래된 ASP.NET 4.7.1 위에서 돌고 있었습니다.

한 일

접근 회복
1차 때 현장에서 시스템 접근과 관리자 계정을 먼저 되찾았습니다. 이 단계 없이는 로그도 프로세스도 확인할 수 없었습니다.
로그 분석
IIS 로그를 따라가며 응용프로그램 풀 안에서 정상 앱이 아닌 실행을 찾았고, 이를 루트킷으로 판단했습니다. 구형 미들웨어와 웹 필터에 남아 있던 취약점을 점검하고 조치했습니다.
CVE 대조
2차 사고에서는 서버가 쓰던 ASP.NET 4.7.1과 관련 구성 요소를 공개 CVE 목록과 하나씩 대조해, 노출된 취약점을 좁혔습니다.
데이터 격리
2차 사고 뒤 서버를 새로 세우는 쪽으로 의사결정을 도왔습니다. MSSQL 데이터는 내부망의 격리된 PC로 옮겨 무결성을 확인했습니다.
AWS 재구축
웹 애플리케이션은 AWS EC2에 새로 세우고 DB는 RDS로 옮겼습니다. Security Group은 운영 IP 허용목록만 열고 RDP 접근을 막았습니다.
재발 방지 권고
VPN 도입, 프레임워크 업그레이드, 클라우드 이관을 권고안으로 정리했습니다. 기술 담당자에게는 취약한 구성과 코드 문제를, 경영진에게는 서비스 중단과 복구에 드는 비용을 따로 설명했습니다.

비용과 시간으로 설명한 과정

파트너사 담당자는 보안 조치에 그만한 비용을 써야 하는지, 같은 사고가 또 나지 않는지를 걱정했고 서비스 복구 말고는 관심이 크지 않았습니다. 그래서 기술 용어로 설득하는 대신 비용과 걸리는 시간을 그래프와 도형으로 보여 줬습니다.

위험이 얼마나 줄어드는지는 기존 .NET Framework 버전과 업데이트 버전의 CVE 수, 사고 빈도를 자료로 삼아 AI를 활용해 추정치를 만들었고, 출처를 남겼습니다.
