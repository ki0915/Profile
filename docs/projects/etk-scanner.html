도구 사례2026.07

ETK-Scanner, 비용 상한이 있는 LLM 소스코드 취약점 진단

정적분석으로 의심 구간을 먼저 좁히고 LLM 검증은 필요한 곳에만 쓰는 취약점 스캐너를 만들어, 실습 백엔드와 오픈소스의 권한 문제를 찾았습니다.

역할
파이프라인 설계, 구현, 검증

풀려던 문제

위험 함수 호출만 찾는 규칙 기반 도구는 권한 우회나 검증 우회처럼 위험 함수 없이 생기는 결함을 잡지 못합니다. 모든 함수를 LLM에 보내면 비용 때문에 CI에 붙이기 어렵습니다. 비용 대비 효율이 좋은 취약점 진단 도구를 만들고자 시작했습니다.

고른 설계와 이유

비용이 적은 단계부터 거르도록 정적분석, 저비용 모델 분류, 고비용 모델 검증 순서로 나눴습니다.

후보에는 eval 같은 위험 함수와 함께 validate나 auth처럼 보안 판단을 하는 함수를 넣었습니다. 권한 우회나 검증 우회는 위험 함수 호출 없이도 생기기 때문입니다.

직접 설계하고 만든 것

  • Python 코드는 AST로, JavaScript와 TypeScript는 정규식으로 보안 판단 함수를 후보로 뽑습니다. 이 단계는 LLM 비용이 들지 않습니다.
  • 저비용 모델이 후보마다 한 번 분류하고, 남은 소수만 고비용 모델이 여러 차례 문맥을 확인하며 검증합니다.
  • 모든 LLM 호출의 비용을 기록하고, 정한 예산에 닿으면 분석을 멈춥니다.
  • 결과를 SARIF로 내보내 GitHub 보안 탭에 올리고, GitHub Actions에서 PR과 push마다 정적 모드를 돌려 검사가 실패하면 job을 실패로 처리합니다.

함께 쓰고 고친 과정

이 스캐너를 활용해 한 오픈소스 프로젝트의 인가 처리 문제를 소스 수준에서 분석했습니다. 재현 자료와 원인 분석을 유지관리자에게 보냈고, 영향 확인과 수정 예정 회신을 받았습니다. 공개 전이라 프로젝트 이름과 세부 내용은 적지 않습니다.

검증 방법

직접 만든 TypeScript 실습 백엔드를 검사하자 소스에 박힌 JWT 서명 키가 잡혔습니다. 이 키를 알면 누구나 토큰을 위조할 수 있습니다. 키를 환경변수로 옮기기 전과 후를 실제 HTTP 서버로 비교했습니다.

공개 SecurityEval 데이터의 취약 코드에도 스캐너를 돌려 몇 개를 찾는지 확인했습니다.

로컬 코드 확인 2026-10-16

기능 명세

기능하는 일확인
보안 판단 함수 탐지Python 코드는 AST로, JavaScript와 TypeScript 코드는 정규식으로 읽어 보안 판단이 들어간 함수를 후보로 뽑습니다.공개 SecurityEval 데이터의 취약 코드 121개에 스캐너를 실행해 111개를 탐지했습니다.
단계별 LLM 검증저비용 모델이 후보마다 한 번 질의해 취약점 가설과 신뢰도를 매기고, 남은 소수 후보만 고비용 모델이 여러 차례 질의하며 검증합니다.
비용 기록과 예산 상한모든 LLM 호출의 토큰과 비용을 누적해 기록하고, 정한 예산에 닿으면 분석을 멈춥니다.
SARIF 출력탐지 결과의 CWE, 심각도, 파일과 행 위치를 SARIF 2.1.0으로 변환해 GitHub 보안 탭에 올릴 수 있게 합니다.
CI 연동GitHub Actions에서 PR과 push에는 기본 정적 모드를 돌리고 LLM 모드는 수동으로 실행하며, 검사가 실패하면 마지막 job을 실패로 처리합니다.

시연

만든 방법

  1. 후보 추출Python AST와 JS, TS 정규식으로 보안 판단 함수를 넓게 뽑으며, 이 단계에는 LLM 비용이 들지 않습니다.
  2. 저비용 분류한 번의 질의로 후보마다 취약점 가설과 신뢰도를 매겨 검증할 대상을 줄입니다.
  3. 고비용 검증남은 소수 후보만 여러 차례 질의하며 코드를 따라가 검증합니다.
  4. 필터와 중복 확인기능 버그와 보안 취약점을 나누고, OSV 데이터베이스에서 이미 알려진 취약점인지 조회합니다.
  5. 결과 출력남은 결과를 SARIF 2.1.0으로 내보내고, 모든 단계의 호출 비용을 합산해 기록합니다.
