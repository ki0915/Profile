CASE-04도구 사례2026.07

Mcp-Guard, LLM과 MCP 통신의 개인정보 유출 방지 프록시

LLM과 MCP 도구로 나가는 요청에서 주민등록번호와 API 키 같은 민감 정보를 찾아 가리거나 막는 프록시를 만들었습니다.

역할
정책과 탐지 설계, 구현, 검증
직무
보안, AI 보안
저장소
github.com/ki0915/Mcp-Guard

처리 흐름

  1. 01받기HTTP 리버스 프록시와 stdio 어댑터가 요청과 응답을 받습니다
  2. 02풀어 보기NFKC 정규화, 숫자 사이 공백과 보이지 않는 문자 제거, 크기를 제한한 Base64 디코딩
  3. 03찾기주민등록번호, 카드, 계좌, 시크릿, 조직 기밀 탐지기가 위치를 찾습니다
  4. 04판정정책에 따라 가리기, 막기, 경보 가운데 하나를 고르고, 판단이 어려우면 막습니다
  5. 05기록원래 값을 뺀 감사 로그와 Prometheus 지표를 남깁니다

해결한 문제

  1. 문제

    HTTP만 보는 프록시는 stdio MCP 서버에 닿지 못함

    쓴 것

    줄 단위 JSON-RPC를 검사하는 stdio 어댑터

    효과

    두 통신 경로에 같은 정책을 적용

  2. 문제

    띄어 쓴 번호, 전각 숫자, Base64로 감싼 값이 통과

    쓴 것

    원문 위치를 유지하는 정규화 뒤 검사

    효과

    합성 우회 사례 탐지가 크게 늘어남

  3. 문제

    실제 기밀값이 설정 이력에 남을 위험

    쓴 것

    기밀값은 Kubernetes Secret에만 두고 해시로 대조

    효과

    ConfigMap과 Helm 이력에 원래 값이 남지 않음

  4. 문제

    원문을 그대로 보내는 경보 설정으로 정책이 약해질 위험

    쓴 것

    주민등록번호, 카드, 시크릿은 경보로 낮출 수 없게 함

    효과

    고위험 값은 항상 가리거나 막음

배경

풀려던 문제

생성형 AI를 업무에 쓰면 사람이 붙여 넣은 문서나 로그에 개인정보와 시크릿이 섞이기 쉽습니다. MCP 서버는 표준 입출력으로 JSON-RPC 메시지를 주고받는 경우가 많습니다. 그래서 네트워크 경계에 둔 HTTP 프록시만으로는 내용을 볼 수 없습니다.

문제를 확인한 방법

처음 버전은 원문 그대로만 검사했고, 띄어 쓴 주민등록번호나 전각 숫자, Base64로 감싼 값이 그대로 통과했습니다. 우회 기법을 넣은 합성 데이터로 그 차이를 쟀습니다.

고른 설계와 이유

HTTP 프록시와 stdio 어댑터에 같은 정책을 적용해 두 경로의 판단이 같게 했습니다. 검사는 원문 위치를 유지한 파생 문자열로 하고, 마스킹은 원래 입력의 해당 범위에 적용했습니다. 판단이 어려우면 막고, 감사 로그에는 원래 값을 남기지 않게 했습니다.

직접 설계하고 만든 것

  • HTTP 리버스 프록시는 요청과 응답 본문, URL, SSE 이벤트를 검사하고, stdio 어댑터는 MCP의 줄 단위 JSON-RPC를 같은 정책으로 검사합니다.
  • 주민등록번호는 날짜와 검증 숫자로, 카드번호는 IIN과 Luhn 검사로, 계좌번호는 앞뒤의 은행 문맥으로 확인합니다.
  • 유니코드 NFKC 정규화, 숫자 사이 공백과 보이지 않는 문자 제거, 크기를 제한한 Base64 디코딩으로 우회 표현을 풀어 검사합니다.
  • 정책 스키마 검증과 시크릿 분리, 만료 시간이 있는 허용 예외, Prometheus 지표, Dockerfile과 Helm 차트를 만들었습니다.

기능

  • HTTP 리버스 프록시

    요청과 응답 본문, URL, SSE 이벤트까지 검사합니다

  • stdio MCP 어댑터

    MCP 서버를 자식 프로세스로 띄워 양방향으로 검사하고, 막으면 JSON-RPC 오류를 돌려줍니다

  • 한국 개인정보 탐지

    주민등록번호 검증 숫자, 카드 Luhn, 계좌 은행 문맥으로 확인합니다

  • 보호값 레지스트리

    조직이 정한 기밀값을 해시로만 저장해 대조합니다

  • 감사 로그와 지표

    원래 값 없이 JSON Lines로 남기고 Prometheus로 보냅니다
